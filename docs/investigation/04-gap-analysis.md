# 04 — Gap Analysis

Spec-by-spec. `Status ∈ EXISTS | PARTIAL | MISSING | CONFLICTS`. Specs 01, 02, 04 are anchored to their real text in `plans/`. **Spec 03 is not in the repo** — it is analysed from the investigation brief's description (Owner Digest · Receivables · Stock Alerts).

`CONFLICTS` = the spec asks for something incompatible with how the code works; each has a proposed alternative.

## Cross-spec: ordering constraints, hidden work, blast radius

- **Ordering forced by the code:** **Epic 0 (integer-XAF money)** precedes Specs 01–02 (their arithmetic + acceptance tests require it). **PIN prerequisite** precedes the authorization parts of Specs 01 **and** 02 (shared). **Spec 02 shifts** precede Spec 04's `business_date`. Spec 03's stock-alert/ageing pieces can ship **early** (already built).
- **Hidden work no spec mentions:** (1) every new table/column needs **two** migrations (Postgres + SQLite) + sync-graph registration + a hand-written column map, or it won't sync; (2) a **desktop test harness** (`apps/desktop-v2`/`electron-core` have zero tests today) before trusting any local-first money/cash logic; (3) domain rules must be implemented **twice** (server + desktop) and kept in parity; (4) DB-level append-only enforcement.
- **Blast radius / coverage:** Specs 01–02 touch the **sale write path** (has API tests, **no desktop tests**), **inventory** (`deduct-for-sale.spec.ts` exists), **daily-summary**, **expenses** (new cash link). The audit changes touch every emit site. The money migration touches **everything**. Protective coverage is server-only; the offline path — where these specs live — is unguarded.
